# Case Study: EC2 + RDS Three-Tier Application

## Summary
Built a classic three-tier web application on AWS. An EC2 instance in a public subnet runs a Python Flask app, which connects to a managed PostgreSQL database (RDS) in a private data subnet. Access is secured via Secrets Manager and SSM, with no hardcoded passwords or open SSH ports.

## The problem
Web applications need to serve traffic to the internet while keeping databases completely isolated. Hardcoding database passwords in code or leaving SSH ports open are common security failures that lead to breaches. 

## What I built
- **App Tier:** EC2 (t3.micro) running nginx and a Python Flask app.
- **Data Tier:** RDS PostgreSQL (db.t3.micro) in a private subnet.
- **Security Group Chaining:** The database security group only allows traffic on port 5432 from the app server's security group. 
- **Secrets Management:** Terraform generates a random password and stores it in AWS Secrets Manager. The EC2 instance retrieves it at boot via its IAM role.
- **Access:** SSM Session Manager is used for administrative access, eliminating the need for SSH keys or bastion hosts.

## Architecture

   [ Internet ]
        |
   [ Public Subnet ] ---> [ EC2 (nginx + Flask) ] 
                               |
                               | (Port 5432)
                               v
   [ Private Subnet ] ---> [ RDS PostgreSQL ]

## Security decisions
- **No SSH:** Port 22 is completely closed on the app server. Access is exclusively via SSM, which logs every command to CloudTrail.
- **Database Isolation:** RDS is deployed with `publicly_accessible = false` and placed in a private data subnet with no route to the internet. 
- **Least Privilege:** The EC2 IAM role can only read the specific secret ARN it needs and use SSM. It has no other AWS permissions.
- **Secrets Management:** The database password is 24 characters, generated by Terraform, and never printed to the terminal. It is injected into the Flask app via systemd environment variables at runtime.

## Challenges and how I solved them

**RDS Version Deprecation:** Attempted to deploy PostgreSQL 16.3, but AWS returned `InvalidParameterCombination`. AWS had deprecated that exact minor version. Fixed by changing the Terraform variable to `engine_version = "16"`, allowing AWS to select the current supported minor.

**Terraform `user_data` Lifecycle Trap:** The initial `user_data` script attempted to fetch the DB password from Secrets Manager, but failed with `ResourceNotFoundException` because RDS (and the secret value) were still being created. EC2 booted too fast.
- *Attempted Fix:* Switched the Python app to fetch the secret dynamically via `boto3` at runtime, removing the dependency on the environment variables and race conditions.
- *The Trap:* Terraform updated the `user_data` metadata in-place, but did not reboot the instance. The EC2 instance kept running the old, cached, broken script.
- *Final Fix:* Used the `terraform apply -replace="aws_instance.app_server"` flag to explicitly destroy and recreate the instance, forcing the new script to execute on first boot.

**AMI Drift:** The second `terraform apply` forced EC2 replacement because `most_recent = true` on the Amazon Linux 2023 AMI filter detected a newly released image. In production, this is managed via launch templates or pinned AMI IDs.

**Startup Time:** The `user_data` script takes about 2-3 minutes to install Python, nginx, and fetch the secret. The app returns a 502 Bad Gateway until the script finishes.

## Results
- Successfully deployed a 3-tier architecture.
- Flask app connects to RDS and executes SQL queries successfully.
- Confirmed database is unreachable from the public internet (`Connection refused` on port 5432).
- Zero passwords or SSH keys stored in the repository.
